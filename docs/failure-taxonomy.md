# 失败码表 F0–F4（统一失败分类）

> 配套：[judge-schema.md](judge-schema.md) §5（failure_rules 字段定义）。
> 本表是**全链单一权威**：判分器输出、人工盲标、增广过滤、评测报告、RAFT 归因共用同一套码。
> 修改码表 = 修改 schema = 递增 `criterion_version` 并全量重判。

---

## 1. 总则

1. **互斥且穷尽**：每条 episode 终局归入恰一类——`success` 或 F0–F4 之一，不存在"落不进任何类"的 episode（F4 为兜底）；
2. **判定优先级固定**（评估器内建，不可配置）：

   ```
   1. F0      指标缺失/不可读（工具故障优先暴露）
   2. sticky  粘滞失败标志已置位（灾难性失败不可恢复）
   3. success hold_timer 达标（按 latch 语义收尾）
   4. 失败规则链 按 YAML failure_rules 声明顺序逐条判定
   5. 兜底    default: true 规则
   ```

3. **证据自证**：每条失败输出必须携带实际值 vs 阈值（`MetricEvidence`），人工复核无需回放视频；
4. **F0 不是任务失败**：F0 表示判分工具自身故障，必须修复后重跑，**不得计入**一致率统计与成功率分母。

## 2. 码表

### F0 · 传感器/判分器异常（工具故障）

| 项 | 内容 |
|---|---|
| 定义 | 判分所需的指标源不可读（位姿读取失败、关节状态缺失），判分器自身无法给出可信结论 |
| YAML 表达 | `{"id": "F0", "when": "metric_missing"}` |
| 证据指标 | 哪个 source 的哪个指标缺失、自哪一步起缺失 |
| 粘滞 | 无意义（F0 优先级最高，直接终局） |
| 人工直觉 | "裁判设备坏了"，不是"选手失败" |
| 处理动作 | **修复适配器/传感器 → 重跑**。不计入一致率统计（人工标注也不将其作为失败样本）；反复出现 F0 视为适配器缺陷，阻塞发布 |

### F1 · 抓取失败（粘滞）

| 项 | 内容 |
|---|---|
| 定义 | 搬运过程中发生灾难性失败：物体跌破高度线、倾角超过限值 |
| YAML 表达 | `{"id": "F1", "sticky": true, "conditions_any": [obj_z < 高度线, obj_tilt_deg > 限值(ref: initial)]}` |
| 证据指标 | 触发瞬间的 obj_z / obj_tilt_deg 实际值与阈值 |
| 粘滞 | **是**——一旦触发，此后无论轨迹如何整条判死 |
| 人工直觉 | "掉了/翻了就是失败"，**先掉后捡回不算成功**（对抓取搬运任务是合理语义：中间状态已污染后续数据质量） |
| 处理动作 | 正常失败类；归因时结合逐维信号判断抓取策略问题 |

### F2 · 放置偏移

| 项 | 内容 |
|---|---|
| 定义 | 物体**曾进入**成功区域，但连续保持时长不足 `hold_s`（或 latch: false 时终局不在区域内） |
| YAML 表达 | `{"id": "F2", "when": "entered_region_without_hold"}` |
| 证据指标 | 最长连续保持时长 `hold_s_achieved` vs 要求 `hold_s`；进入区域的帧区间 |
| 粘滞 | 否 |
| 人工直觉 | "碰到了但没放稳/没停住"——比 F4（从未接近）更接近成功，策略改进优先级更高 |
| 处理动作 | 与 F4 分开统计——F2 多 = 抓取后放置控制欠佳；调 hold 阈值前先查抖动（见下） |

> 边界注意：hold_timer 离开区域即**清零**（非暂停），分段累计不等于连续保持。高频抖动（区域内↔外交替）会落在 F2——若抖动来自传感器噪声而非真实运动，先加平滑/稳定判据（`obj_z_step_delta`），**不许放宽 hold_s**。

### F3 · 设备状态未达成

| 项 | 内容 |
|---|---|
| 定义 | 任务要求的设备状态量（关节角、门/盖状态、设定值）全程未进入阈值区域 |
| YAML 表达 | 兜底前的显式规则，或关节角类任务的 `default: true` |
| 证据指标 | 全程该指标的最大/最小实际值 vs 阈值（如 joint_angle_deg 最大 -50 vs 阈值 -46） |
| 粘滞 | 否 |
| 人工直觉 | "盖子根本没合到位"——设备交互环节失败，与物体搬运（F1/F2）不同环节 |
| 处理动作 | 检查设备控制策略与铰链方向/行程建模是否正确（阈值方向写反是常见成因） |

### F4 · 流程中断/超时（兜底）

| 项 | 内容 |
|---|---|
| 定义 | 以上全部未命中：物体从未接近目标区域，或 episode 超时被外层截断 |
| YAML 表达 | `{"id": "F4", "default": true}`（全表**恰一条**） |
| 证据指标 | 终局时刻与目标的最小距离、超时时长 |
| 粘滞 | 否 |
| 人工直觉 | "还在半路/迷路了"——最早期失败，通常意味着策略未学到任务结构 |
| 处理动作 | 与 F2 的比例是策略诊断信号：F4 占比高 → 任务级失败（没学会）；F2 占比高 → 接近成功（差最后一步） |

## 3. 与人类标注的对应

- 人工盲标使用**同一套码表**（标注表附本页链接 + 每类一个示例视频）；盲标者不可见判分器输出；
- 一致率在**成败二值**层面卡线（T4 验收 ≥95%）；失败**分类**层面的一致率（混淆矩阵）作为质量指标记录、不卡线；
- 标注分歧的归因四分类：阈值校准问题 / 分类歧义（本表定义漏洞）/ 标注错误 / 判分器 bug——修表必须走 `criterion_version` 递增 + 全量重测。

## 4. 输出契约

- CSV（人看）：`fail_reason` ∈ {`success`, `F0`, `F1`, `F2`, `F3`, `F4`}；`fail_class` 为本表的可读名；
- JSON（机器）：`EpisodeResult.to_json_dict()` 全量输出 `metrics` 证据与 `per_step_success` 逐帧标记；
- 成功时 `fail_reason` 恒为字符串 `success`（不是空值、不是 "OK"）——消费方按字面量匹配。

## 5. 演化规则

- 新增失败码 = schema 破坏性变更（F 编号冻结，新增走 F5+），评审后发布；
- 修改某码的判定条件（不改语义）= criterion_version 递增；
- 每次修改在本文件"变更记录"追加一行。
